# AGENTS.md — instructions for AI agents

> **State:** requirements are still being elaborated. This file describes the project's rules
> for any agent working in it. The repository already contains contracts, frontend and
> scripts; the build and test commands are documented below.

## Before doing anything

1. Read the `AGENTS.md` closest to the files you intend to change.
2. Check `git status --short` to preserve existing work in the workspace.

## Scope: what can be done without asking

**Allowed without asking:**
- Read any file
- Fix a factual error, a dead link, or an inconsistency between documents
- Add detail to an existing document when it is verifiable

**Ask before:**
- **Creating a new file**
- **Installing any dependency** (`npm install`, `cargo add`, `rustup target add`)
- **Changing a recorded decision** in any `AGENTS.md`
- **Resolving an open question** — open questions are open because a person has to decide,
  not because nobody thought of them
- `git commit`, `git push`, or any operation that publishes something
- Deploying to any network, even testnet

**Never:**
- Invent a decision that was not made. If a document needs an answer that does not exist,
  **write the question**, not the answer
- Commit secrets, keys, or identities (`stellar keys`), even on testnet

## Conventions

### Documentation language
The **README** and the **AGENTS.md** files are in English. The *game* is trilingual
(PT-BR/EN/ES via i18n). Do not translate the game content.

### Documentation
- Every file opens with a **State** section
- Factual claims must be verifiable; do not add verification dates
- Measured numbers and estimated numbers are marked as such, separately
- Link between documents with relative paths, always

### Code
- **Rust/Soroban:** `soroban-sdk` on an **exact version, on the `28.x` line** — never `>=`.
  The **security floor** is 25.1.1 (CVE-2026-26267); 28.x is the **choice**, because that is
  where `ExternalRef` exists — the class that is the project's thesis. `stellar-cli` follows
  the same line.
- **TS/React:** no `any`; the `Client` generated by the bindings is the source of types
- Formatting: `cargo fmt` for Rust, Prettier for TS

## Project rules

These five rules are **security invariants**, not style preferences. Each one exists because
the previous falls if it falls.

> **1. The core cannot hold state the player can change.**
>
> The player is an adversary — and that is what the game *wants* them to be. If they can
> write anything the core — or the validator — reads at validation time, validation stops
> meaning anything.

> **2. The instance is disposable. The core is sacred.**
>
> The instance state **must** be fully destroyable by the player — that is literally the
> game's objective. It is not part of the architecture and may even be destroyed entirely.
> The core is not. The validator is not either: it **has no state** — what it reads is the
> instance.

> **3. The player never interacts with the validator directly.**
>
> The **core** creates instances and holds ownership and progress; the **validator**, one per
> level, decides whether the objective was met. The player talks to the **instance** and to
> the **core** — creating the instance and submitting the solution are their transactions,
> and there is no way around that. What they **never** touch is the validator: if the
> validator becomes an attack surface, rules 1 and 2 fall with it.

> **4. Every level has two tests — and they run against the deployed WASM, not only against
> `cargo test`.**
>
> One test asserts the objective is **not** met at the start; the other runs the exploit and
> asserts it now is. Without the first, there is no way to tell a solvable level from one
> that is already "solved" — and a level that is already solved passes any exploit test.
>
> "Against the deployed WASM" is not pedantry: `cargo test` runs the native crate, while the
> game runs the WASM built by `stellar contract build`. **A test that passes under
> `cargo test` does not prove that the WASM is what was deployed.**
>
> The release profile keeps `overflow-checks = true` on purpose, so the harness and the
> deploy agree about overflow.

> **5. No level exposes a path to replace its own WASM.**
>
> `update_current_contract_wasm` **has no built-in authentication** — but **only the contract
> itself can call it**. There is no host function that replaces *another* contract's
> executable. So the defense is omission, and it is enough: with no upgrade entrypoint, the
> instance is **immutable in practice**.
>
> **Why this is an invariant, not style:** an upgrade **preserves storage** — only the
> `executable` field changes. If the player replaces the instance's code, they start writing
> the state the validator reads. Validation **reads state** instead of listening to the
> instance; without this rule, that gain is lost through another path.
>
> It applies to **indirect** paths: any public function that takes `BytesN<32>` and reaches
> `update_current_contract_wasm`, and the executable refs registry (`ExternalRef`,
> protocol 28+), which lets one contract control another's executable.

## Sources of truth

Precedence when two sources disagree:

1. **The contract source / the deployed WASM** — what executes is the truth
2. **The official SDF documentation** (`developers.stellar.org`)
3. **The contract spec** (`spec.funcs()` / `spec.jsonSchema()`) — the real interface, not the
   one someone remembers
4. **This repository** (`AGENTS.md`, `README.md`) — for what is already established here
5. **Blogs, Medium, LLM answers** — not sources. If it only exists there, it is not verified

**Recurring trap:** the public TTL documentation shows **mainnet** values. On testnet the
minimum is **7 days**, not 120.

## Build and test

```bash
# Contracts: the WASM first, the tests after.
cd contracts && ./build.sh && cargo test

# Frontend: types, suite and build (they include the level catalog guard).
cd frontend && npx tsc --noEmit && npm test && npm run build

# Scripts: local probes with a simulated CLI; no network.
./scripts/ci.sh scripts
```

⚠️ **`cargo build` alone does not build a contract.** The SDK's `build.rs` requires
`stellar contract build`, which is what `contracts/build.sh` calls. A
`cargo build -p breaker-level-NN-instance` fails with *"soroban-sdk requires stellar-cli
v25.2.0+"* — **that is not a defect**, it is the recipe.

⚠️ **`cargo test` reads the WASMs from disk**, so `./build.sh` comes first. A test that fails
after a contract change is usually an old WASM, not a wrong test.

**The TypeScript bindings are generated by `scripts/deploy.sh`**, and only for the core.
There is no separate command: they are a deploy step, and what is versioned under
`frontend/src/contracts/` is the result.

**The test that guards the project structure** is `frontend/src/levels/manifest.test.ts`. It
checks that `levels.json`, the disk, the workspace `Cargo.toml`, the test modules and the
content in all three languages agree. Before adding a level, use `scripts/new-level.sh` —
the path is one command.
